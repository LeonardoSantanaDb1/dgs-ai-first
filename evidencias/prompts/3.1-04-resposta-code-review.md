# Resumo executivo

O módulo está bem estruturado para um primeiro ciclo: separação de responsabilidades clara, uso correto de Zod com `safeParse`, fallback explícito e logs com contexto.

Contudo, há problemas que vão de severidade alta a baixa que precisam ser endereçados antes de ir para produção — especialmente na confiabilidade do Guardrail 2, na ausência de imutabilidade do fallback e em riscos de log injection.

# Problemas encontrados

## 🔴 Alta — Guardrail 2: regex de texto livre sem `\b` e sem cobertura de negações

### Trecho

```ts
const mentionsReturnAllowed =
  normalized.includes("devolucao e permitida") ||
  normalized.includes("pode ser devolvido") ||
  // ...
```

### Motivo técnico

`String.prototype.includes` com frases fixas é frágil demais para linguagem natural.

A frase:

> "a devolução não é permitida para carga perigosa"

contém os tokens **carga perigosa** + fragmentos de **devolucao** + **permitida** dispersos.

Dependendo da tokenização mental do revisor, a lógica aparenta cobrir, mas não cobre negações.

Além disso, variações semânticas triviais como:

- autorizado devolver
- retorno liberado
- pode ser retornado

passam inteiramente despercebidas.

### Impacto

Taxa de falsos negativos potencialmente alta.

O guardrail mais crítico do ponto de vista de compliance é exatamente o que tem a cobertura mais fraca.

Em produção, respostas de risco real passariam pelo filtro.

### Sugestão

Substituir `includes` por `RegExp` com `\b` (word boundary) e adicionar ao menos as variantes semânticas mais previsíveis.

Considerar uma lista de termos de "permissão" (permitid, autorizado, liberado, pode, aceita) combinada via regex composta, documentando explicitamente o que não é coberto.

## 🔴 Alta — SAFE_FALLBACK_RESPONSE é mutável em runtime

### Trecho

```ts
export const SAFE_FALLBACK_RESPONSE: ModelResponse = {
  answer: "Não foi possível...",
  source_document: "FALLBACK_SYSTEM",
  confidence_score: 0,
};
```

### Motivo técnico

`const` em TypeScript impede reatribuição da variável, mas não congela o objeto.

Qualquer código importador pode fazer:

```ts
SAFE_FALLBACK_RESPONSE.answer = "resposta maliciosa";
```

sem erro em tempo de compilação nem em runtime.

Em um contexto de harness de segurança, isso é uma falha estrutural.

### Impacto

O objeto de fallback pode ser mutado acidentalmente (ou intencionalmente) por qualquer módulo que o importe, subvertendo a garantia de resposta segura.

### Sugestão

```ts
export const SAFE_FALLBACK_RESPONSE: Readonly<ModelResponse> =
  Object.freeze({
    ...
  });
```

## 🔴 Alta — Log injection via campo answer não sanitizado

### Trecho

```ts
logger.warn(
  { answerSnippet: response.answer.slice(0, 120) },
  "Resposta bloqueada por guardrail."
);
```

### Motivo técnico

O conteúdo de `answer` vem do modelo e não é sanitizado antes de ser logado.

Se o transporte de log for texto/JSON sem escape correto (ex.: log agregador legado, stdout em formato texto), uma resposta do modelo contendo:

- `\n`
- sequências ANSI
- fragmentos JSON

pode quebrar a estrutura do log ou injetar entradas falsas.

### Impacto

Em pipelines de log com parsing textual ou SIEM, um modelo adversarial poderia injetar entradas de log falsas, dificultando auditoria e alertas.

### Sugestão

Sanitizar o snippet antes de logar:

```ts
const safeSnippet = response.answer
  .slice(0, 120)
  .replace(/[\r\n\t]/g, " ");
```

## 🟡 Média — Schema Zod aceita answer com conteúdo de whitespace puro

### Trecho

```ts
answer: z.string().min(1, "O campo 'answer' não pode estar vazio."),
```

### Motivo técnico

`min(1)` valida comprimento da string, não seu conteúdo.

A string:

```text
"   "
```

tem `length === 3` e passa na validação.

O modelo poderia retornar uma resposta tecnicamente não-vazia mas semanticamente vazia.

### Impacto

O atendente recebe uma resposta em branco sem que nenhum guardrail dispare.

Falha silenciosa do pipeline de validação.

### Sugestão

```ts
answer: z
  .string()
  .min(1)
  .refine(v => v.trim().length > 0, {
    message: "O campo 'answer' não pode conter apenas espaços em branco."
  }),
```

Aplicar o mesmo para `source_document`, que possui o mesmo risco.

## 🟡 Média — source_document aceita valores arbitrários sem allowlist

### Trecho

```ts
source_document: z.string().min(1, "..."),
```

### Motivo técnico

O schema valida apenas que o campo é uma string não-vazia.

Um modelo alucinado pode retornar:

```text
documento_inventado_123.pdf
```

e o Guardrail 1 passa sem disparar.

O campo não é validado contra nenhum conjunto de documentos conhecidos do índice do Azure AI Search.

### Impacto

Grounding falso.

A resposta aparenta possuir fonte, mas a fonte não existe no corpus.

O atendente pode citar um documento inexistente para o cliente.

### Sugestão

Injetar no validator (via parâmetro ou DI) uma lista/set de document IDs válidos recuperados do índice e validar com `.refine()`.

Caso não seja viável, registrar um warning específico para documentos desconhecidos.

## 🟡 Média — confidence_score validado mas sem guardrail de threshold

### Trecho

```ts
confidence_score: z.number().min(0).max(1),
```

### Motivo técnico

O campo existe, é validado estruturalmente e é logado.

Mas uma resposta com:

```json
confidence_score: 0.05
```

passa por todos os guardrails.

O comentário menciona threshold futuro, porém nenhuma ação ocorre.

### Impacto

Respostas de baixíssima confiança chegam ao atendente sem qualquer indicação.

Viola princípios básicos de Harness Engineering.

### Sugestão

```ts
const LOW_CONFIDENCE_THRESHOLD =
  parseFloat(process.env.LOW_CONFIDENCE_THRESHOLD ?? "0.4");

if (response.confidence_score < LOW_CONFIDENCE_THRESHOLD) {
  logger.warn(
    { confidence_score: response.confidence_score },
    "Resposta com baixa confiança."
  );
}
```

## 🟡 Média — parseModelOutput retorna error como string concatenada

### Trecho

```ts
const messages = result.error.errors
  .map((e) => `[${e.path.join(".")}] ${e.message}`)
  .join("; ");

return {
  success: false,
  error: messages
};
```

### Motivo técnico

Os erros do Zod são serializados em uma única string.

Toda a estrutura do `ZodError` é perdida.

### Impacto

Dificulta observabilidade e evolução do validator.

Não é possível distinguir erros por campo sem fazer parsing textual.

### Sugestão

```ts
return {
  success: false,
  errors: result.error.errors
};
```

## 🟡 Média — Normalização Unicode incompleta para o contexto brasileiro

### Trecho

```ts
const normalized = response.answer
  .toLowerCase()
  .normalize("NFD")
  .replace(/[\u0300-\u036f]/g, "");
```

### Motivo técnico

A normalização cobre apenas diacríticos básicos.

Não cobre:

- homoglifos
- abreviações
- siglas
- variações com hífen
- carga-perigosa
- devol.

Também não é aplicada ao `source_document`.

### Impacto

O Guardrail 2 pode ser burlado com pequenas variações tipográficas.

### Sugestão

Extrair a normalização para uma função utilitária reutilizável e documentar claramente seu escopo.

## 🟢 Baixa — GUARDRAILS tipado como ReadonlyArray mas funções não são readonly

### Trecho

```ts
const GUARDRAILS: ReadonlyArray<
  (r: ModelResponse) => GuardrailResult
> = [
  checkSourceDocument,
  checkDangerousCargoReturn,
];
```

### Motivo técnico

O array é imutável, mas as funções continuam mutáveis.

Não é um bug.

É apenas uma pequena inconsistência conceitual.

### Impacto

Baixo.

### Sugestão

Adicionar um comentário explicando a intenção ou manter como está.

## 🟢 Baixa — Log de sucesso em nível info pode gerar volume excessivo

### Trecho

```ts
logger.info(
  {
    source_document: response.source_document,
    confidence_score: response.confidence_score
  },
  "Resposta validada com sucesso."
);
```

### Motivo técnico

O caminho feliz produz um log `info` para cada requisição.

Em produção isso gera alto volume.

### Impacto

- aumento de custo
- ruído em dashboards
- maior consumo de armazenamento

### Sugestão

Utilizar:

```ts
logger.debug(...)
```

e reservar `info` para eventos relevantes.

---

## 🟢 Baixa — GuardrailResult.reason deveria ser obrigatório quando blocked = true

### Trecho

```ts
interface GuardrailResult {
  blocked: boolean;
  reason?: string;
}
```

### Motivo técnico

Quando:

```text
blocked === true
```

o campo `reason` deveria obrigatoriamente existir.

Hoje isso não é garantido.

### Impacto

Um guardrail poderia bloquear uma resposta sem informar o motivo.

### Sugestão

Utilizar uma **Discriminated Union**:

```ts
type GuardrailResult =
  | {
      blocked: false;
    }
  | {
      blocked: true;
      reason: string;
    };
```

# Síntese

| Severidade | Quantidade | Principais itens |
|------------|-----------:|------------------|
| 🔴 Alta | 3 | Guardrail 2 frágil, fallback mutável, log injection |
| 🟡 Média | 5 | Whitespace em answer, allowlist de documentos, threshold de confiança, perda da estrutura do ZodError, normalização incompleta |
| 🟢 Baixa | 3 | Readonly parcial, excesso de logs no caminho feliz, GuardrailResult sem discriminated union |

## Conclusão

Os três itens classificados como **Alta** devem ser resolvidos antes de qualquer deploy.

Os itens de **Média** representam dívida técnica que afeta diretamente a confiabilidade dos guardrails em produção.

Os itens de **Baixa** são melhorias de qualidade e arquitetura que podem ser tratadas posteriormente, sem impacto operacional imediato.
