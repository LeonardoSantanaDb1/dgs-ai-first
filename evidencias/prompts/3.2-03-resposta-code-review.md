# PROBLEMA 01

## Título

**Inicialização de cliente Cosmos dentro do handler por requisição**

**Categoria:** Arquitetura / Performance

**Severidade:** 🔴 Alta

### Trecho

```typescript
const { CosmosClient } = require('@azure/cosmos');
const client = new CosmosClient(process.env.COSMOS_CONNECTION_STRING);
const database = client.database('novatech');
const container = database.container('feedbacks');
```

### Motivo técnico

O `CosmosClient` foi projetado para ser instanciado uma única vez e reutilizado — ele gerencia internamente um pool de conexões TCP persistentes.

Recriá-lo a cada invocação do handler destrói e reconstrói esse pool, gerando overhead de handshake TCP/TLS em cada requisição.

Isso é explicitamente documentado como antipadrão pelo SDK da Microsoft.

### Impacto

- Latência aumentada em todas as requisições;
- Pressão desnecessária no Cosmos (limite de conexões);
- Potencial para throttling sob carga;
- Custos operacionais elevados.

Em Azure Functions com plano Consumption, o efeito é especialmente pronunciado após cold starts.

### Sugestão

Mover a inicialização para o escopo do módulo (fora do handler), aproveitando o ciclo de vida da instância da Function:

```typescript
// escopo do módulo — instanciado uma vez por worker
const cosmosClient = new CosmosClient(process.env.COSMOS_CONNECTION_STRING!);
const container = cosmosClient.database('novatech').container('feedbacks');
```

# PROBLEMA 02

## Título

**require() dinâmico dentro de função async em módulo TypeScript**

**Categoria:** TypeScript / Arquitetura

**Severidade:** 🔴 Alta

### Trecho

```typescript
const { CosmosClient } = require('@azure/cosmos');
```

### Motivo técnico

O uso de `require()` dinâmico dentro de uma função TypeScript é semanticamente incorreto em três frentes:

1. rompe o sistema de módulos ESM/CJS declarado no tsconfig;
2. contorna a verificação de tipos em tempo de compilação — `CosmosClient` chega como `any`;
3. impede tree-shaking e análise estática pelo bundler.

É um import disfarçado de procedural.

### Impacto

- Sem verificação de tipo no uso do cliente;
- Dependência invisível ao analisador de imports;
- Comportamento pode divergir entre ambientes (local vs. Azure), dependendo da configuração de módulos.

### Sugestão

Substituir pelo import estático no topo do arquivo:

```typescript
import { CosmosClient, Container } from '@azure/cosmos';
```

# PROBLEMA 03

## Título

**Ausência total de validação de entrada — body tipado como any**

**Categoria:** Segurança / Qualidade / TypeScript

**Severidade:** 🔴 Alta

### Trecho

```typescript
const body = await request.json() as any;

const feedback = {
  queryId: body.queryId,
  rating: body.rating,
  comment: body.comment,
  attendantEmail: body.attendantEmail,
  ...
};
```

### Motivo técnico

Qualquer payload é aceito sem validação.

- `body.queryId` pode ser `undefined`, `null`, um objeto aninhado ou uma string de 10 MB.
- `body.rating` pode ser `-999` ou `"drop table"`.

O cast `as any` desativa completamente o compilador TypeScript.

Não há:

- contrato de interface;
- schema enforcement;
- sanitização.

Isso representa uma superfície de ataque aberta.

### Impacto

- Persistência de dados malformados no Cosmos DB;
- Possível injection de dados não sanitizados em logs estruturados;
- Ausência de feedback útil ao cliente quando o payload é inválido;
- Violação do princípio de *fail fast*.

### Sugestão

Definir uma interface ou schema Zod (já presente no stack NovaTech conforme contexto do projeto) e validar antes de qualquer processamento:

```typescript
const FeedbackSchema = z.object({
  queryId: z.string().uuid(),
  rating: z.number().int().min(1).max(5),
  comment: z.string().max(2000).optional(),
  attendantEmail: z.string().email()
});
```

# PROBLEMA 04

## Título

**Log de dados pessoais (attendantEmail) sem mascaramento**

**Categoria:** Segurança / LGPD / Observabilidade

**Severidade:** 🔴 Alta

### Trecho

```typescript
console.log('Feedback recebido:', JSON.stringify(feedback));
```

### Motivo técnico

O objeto `feedback` contém `attendantEmail`, um dado pessoal identificável (PII) sob a LGPD.

Serializar o objeto completo para logs significa que endereços de e-mail de colaboradores irão para Application Insights / Log Analytics sem controle de retenção específico para PII.

Isso pode configurar uma violação da LGPD (Lei 13.709/2018) e viola o princípio de minimização de dados.

### Impacto

- Exposição de PII em sistemas de log;
- Impossibilidade de honrar direito de exclusão sem limpar logs;
- Risco de conformidade legal;
- Ausência de correlação por `queryId`, que seria o campo mais útil para diagnóstico.

### Sugestão

Logar apenas campos não PII relevantes para diagnóstico e utilizar Pino:

```typescript
logger.info(
  {
    queryId: feedback.queryId,
    rating: feedback.rating
  },
  'Feedback recebido'
);
```

# PROBLEMA 05

## Título

**Ausência de tratamento de exceções — falhas de infraestrutura são silenciosas**

**Categoria:** Robustez / Observabilidade

**Severidade:** 🔴 Alta

### Trecho

```typescript
await container.items.create(feedback);

return { status: 200, body: 'OK' };
```

### Motivo técnico

Se `container.items.create()` lançar uma exceção (timeout, throttling, credencial expirada etc.), o Azure Functions retornará HTTP 500 com erro padrão.

Não existe:

- try/catch;
- diferenciação de erros;
- resposta padronizada.

### Impacto

- Stack traces potencialmente expostos;
- Diagnóstico impossível;
- Sem tratamento para HTTP 429;
- Feedbacks podem ser perdidos silenciosamente.

### Sugestão

```typescript
try {
  await container.items.create(feedback);

  return {
    status: 201,
    jsonBody: {
      id: feedback.queryId
    }
  };
} catch (error) {
  logger.error(
    {
      error,
      queryId: feedback.queryId
    },
    'Falha ao persistir feedback'
  );

  return {
    status: 500,
    jsonBody: {
      message: 'Erro interno'
    }
  };
}
```

# PROBLEMA 06

## Título

**COSMOS_CONNECTION_STRING sem guarda de variável de ambiente**

**Categoria:** Segurança / Robustez

**Severidade:** 🔴 Alta

### Trecho

```typescript
const client = new CosmosClient(process.env.COSMOS_CONNECTION_STRING);
```

### Motivo técnico

`process.env.COSMOS_CONNECTION_STRING` pode ser `undefined`.

Além disso, a connection string contém a chave primária do Cosmos DB, uma credencial de alto privilégio.

### Impacto

- Falha silenciosa em runtime;
- Diagnóstico difícil;
- Exposição potencial da chave primária.

### Sugestão

```typescript
const connectionString = process.env.COSMOS_CONNECTION_STRING;

if (!connectionString) {
  throw new Error('COSMOS_CONNECTION_STRING não configurada');
}
```

# PROBLEMA 07

## Título

**Resposta HTTP semanticamente incorreta — 200 OK para criação de recurso**

**Categoria:** Qualidade / Arquitetura

**Severidade:** 🟡 Média

### Trecho

```typescript
return { status: 200, body: 'OK' };
```

### Motivo técnico

A semântica HTTP define **201 Created** para criação de recursos.

Além disso, o body `"OK"` viola o padrão JSON esperado.

### Impacto

- Clientes REST podem interpretar incorretamente a resposta;
- Ausência do identificador do recurso criado;
- Contrato inconsistente.

### Sugestão

```typescript
return {
  status: 201,
  jsonBody: {
    id: feedback.queryId,
    timestamp: feedback.timestamp
  }
};
```

# PROBLEMA 08

## Título

**timestamp gerado no handler sem consideração de fuso horário ou idempotência**

**Categoria:** Qualidade / Robustez

**Severidade:** 🟡 Média

### Trecho

```typescript
timestamp: new Date().toISOString()
```

### Motivo técnico

O timestamp representa o momento da persistência e não necessariamente o momento da captura do feedback.

Também dificulta mecanismos de idempotência.

### Impacto

- Duplicatas;
- Correlação difícil;
- Cosmos gera IDs aleatórios.

### Sugestão

Aceitar timestamp do cliente (validado) ou gerar um identificador determinístico utilizando `queryId`.

# PROBLEMA 09

## Título

**Ausência de correlationId / requestId para rastreabilidade distribuída**

**Categoria:** Observabilidade / Governança de IA

**Severidade:** 🟡 Média

### Trecho

```typescript
console.log('Feedback recebido:', JSON.stringify(feedback));
```

### Motivo técnico

O feedback deveria ser correlacionável com:

- query;
- resposta do modelo;
- trace distribuído.

Sem `correlationId`, isso não é possível.

### Impacto

- Perda de rastreabilidade;
- Dificuldade para auditoria;
- Violação de princípios de observabilidade.

### Sugestão

```typescript
const correlationId =
  request.headers.get('x-correlation-id') ??
  crypto.randomUUID();
```

# RESUMO EXECUTIVO

## Classificação

❌ **Não pronta para produção**

## Justificativa técnica

O código apresenta **6 problemas de severidade Alta**, dos quais **4 configuram riscos imediatos** em ambiente de produção.

| Risco | Problema |
|-------|----------|
| Violação de LGPD | PII (`attendantEmail`) exposta em logs sem mascaramento |
| Falha silenciosa em produção | Sem tratamento de exceções; erros do Cosmos retornam HTTP 500 com stack trace |
| Degradação de performance | `CosmosClient` recriado a cada requisição, destruindo o pool de conexões |
| Superfície de segurança aberta | Ausência de validação de entrada aceita qualquer payload |
| Credencial de alto privilégio desprotegida | Connection string sem guarda e sem Managed Identity |
| Endpoint não autenticado | Qualquer agente externo pode gravar feedbacks |

Além disso, a implementação viola sistematicamente práticas já estabelecidas no projeto NovaTech:

- ausência do Pino (logger estruturado);
- ausência do Zod (validação);
- ausência de observabilidade distribuída necessária para um sistema RAG em produção.

O código pode ser utilizado como protótipo de referência para entender a intenção da funcionalidade, mas requer reescrita completa antes de qualquer deploy em ambiente produtivo.
